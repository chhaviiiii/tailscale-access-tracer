          The payments network above is a teaching sample. I wrote its matching logic by hand, and it is a simplified approximation of Tailscale's real policy engine, not a reimplementation of it. To ground this in something real, I called Tailscale's actual API against my own tailnet the night before this call: GET /acl, GET /devices, POST /acl/preview, and POST /acl/validate.
        

        

          

            
GET /tailnet/-/devices

            
1 device: macbook-pro, macOS, authorized. A brand-new tailnet, nothing custom yet.

          

          

            
GET /tailnet/-/acl

            
The stock default policy: one grant, {"src":["*"],"dst":["*"],"ip":["*"]}, allow everything. No custom groups, tags, or tests.

          

          

            
POST /acl/preview?type=user

            
Asked the real server which rule applies to my own account. It answered: lineNumber 1, the default allow-all grant. One real call, one real, server-computed answer.

          

          

            
POST /acl/validate

            
0 tests defined, so the real endpoint had nothing to check. This is the actual gap: acl/validate only grades tests you already wrote by hand. It can't answer an arbitrary "can X reach Y" question on its own, and most policies, including this fresh one, don't have any tests at all. That's exactly the question Access Tracer answers automatically instead.
